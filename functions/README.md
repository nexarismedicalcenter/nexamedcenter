# NEXARIS Cloud Functions

This package starts the Firebase backend for NEXARIS. It currently contains patient profile initialization, the public provider catalog and availability, local appointment reservation and payment endpoints, the patient's initial medical profile, a restricted appointments summary, and a patient Wallet read/payment flow.

## Patient-submitted diagnostic results

The patient portal uses nexaPatientDiagnosticResults, nexaPatientResultUploadStart, nexaPatientResultSubmit, nexaPatientResultUploadCancel, and nexaPatientResultFile. It also lists partner-center results only after the admin marks them `RESULT_AVAILABLE`; `nexaPatientDiagnosticCenterResultFile` signs a five-minute URL only for the patient's own transferred result and CLEAN file, then audits the open. A patient can upload a result only for a validated laboratory or imaging exam on the patient's own prescription and a paid NEXA encounter; the linked prescribing doctor must remain clinically verified. Upload policies write to a private quarantine prefix and expire quickly. The server rechecks file type, exact size, ownership, encounter and prescription, scans every file, moves only CLEAN files to the private submitted-results prefix, then creates the patient result, follow-up grant, claim, audit event and doctor notification. The patient upload-file endpoint issues a five-minute signed URL only for the owner's clean file.

The verified-prescriber inbox uses nexaProviderPatientResults and nexaProviderPatientResultFile. It exposes only the result assigned to that doctor while its follow-up grant remains open. File reads are audited and also use five-minute signed URLs. `nexaProviderPatientResultFollowUp` supports a signed standalone clinical note, a validated prescription, a proposed available teleconsultation slot, and explicit closure of the grant; each action checks the verified prescriber and linked patient in Firestore transactions, writes an audit entry, and sends a minimized in-app notification. Patients see the note/ordonnance and can reserve and pay for a pending proposed slot through the existing NEXA booking flow. `nexaCleanupPatientResultUploads` removes expired quarantine uploads and reopens their exam claims every 15 minutes. These endpoints use Auth, App Check, CORS allowlisting, rate limits and server-side ownership checks; no portal reads Firestore or Storage directly.

Before deployment, configure the NEXA private Storage bucket, private malware scanner and exact scanner URL/audience in the function environment. The Cloud Functions service identity needs invoker access to that scanner and permission to sign short-lived Storage policies and file URLs. Missing, unreachable or non-CLEAN scanner responses fail closed. App Check Web and the production site origin must also be configured. A retention policy for medical documents is still to be defined. This local tranche was not tested or deployed; no scanner, Storage object or production Firebase data was configured or changed here.

## Clinical-record attachments and version history

`nexaClinicalRecordAttachments` serves appointment and standalone clinical records from the static site. Only the assigned, verified doctor with an active clinical window can start uploads or remove files from a draft. A signed, write-once Storage policy targets a private quarantine path; finalization rechecks the owner, MIME type and exact size, scans the file fail-closed, computes SHA-256, moves only CLEAN files to the private clinical prefix, and saves a new immutable record version. Patients can open attachments only on their own finalized records; doctors can open files only while their record access remains active. File reads use audited five-minute signed URLs with no Firebase download token. `nexaClinicalRecordVersions` returns the active doctor's paginated version history. `nexaCleanupClinicalRecordAttachments` retries stale quarantine and deletion-queue cleanup every 15 minutes.

Before enabling this flow, configure the private NEXA Storage bucket, exact `NEXA_MALWARE_SCANNER_URL` and `NEXA_MALWARE_SCANNER_AUDIENCE`, scanner invoker access for the Functions identity, signed Storage policy permissions, website CORS origins and App Check. Missing or unavailable bucket/scanner configuration fails closed. No Storage object or production Firebase data was configured or changed in this local tranche.

## Diagnostic-center result uploads

`nexaDiagnosticProviderOrders` serves the separate static partner portal. It returns only the verified centre's settled orders, exact exam-line metadata and correction reason after validating its link; provider actions advance the laboratory or imaging status sequence, while a refusal creates a manual settlement alert and never initiates a refund. `nexaDiagnosticResultUploadSessions` creates and cancels short-lived upload sessions for verified, publicly listed laboratories and imaging centers. It checks an owned, paid/settled and completed order, the exact exam line and that line's configured file requirements before issuing write-once signed Storage policies to a private quarantine prefix. `nexaDiagnosticResultSubmit` locks the claim, rechecks the provider/order/session and file metadata, rejects duplicates, scans each PDF/JPG/PNG, and moves only CLEAN files into the private result prefix. It then creates a pending-review result and updates the order, claim, audit log and order event transactionally. Correction submissions supersede only the exact prior result that NEXA marked for correction. After admin validation and transfer, the patient list includes the center result; the patient file endpoint signs and audits the patient's private read. The 15-minute cleanup job removes expired/cancelled/failed quarantine objects and releases stale claims.

`site/espace-centre.html` and `site/espace-centre.js` provide the static login, centre-scoped order listing/search/pagination, lab/imaging status actions, result upload and correction submission. Before deployment, apply the exact website origins from `storage.cors.json` to the NEXA bucket and verify the production scanner URL/audience, Cloud Functions identity's scanner invoker access, private Storage bucket and upload-policy permissions, App Check Web and allowed function origins. The portal/backend tranche is local and untested; no production Firebase access/write, Storage upload, deployment, commit or push was performed.

`nexaDiagnosticPublicOffers` returns active, published offers only from verified and publicly listed NEXA laboratories or imaging centers. `nexaDiagnosticOrderCreate` revalidates the patient, up to 10 offers from one verified centre, current prices, appointment requirements and any owned validated prescription inside a Firestore transaction. `nexaPharmacyPublicProducts` returns active, in-stock products of verified, listed pharmacies and active delivery zones. `nexaPharmacyOrderCreate` accepts a maximum of 20 product lines from one pharmacy, validates prescription medication name/DCI, dosage, form and quantity, allocates sellable lots in FEFO order and creates an idempotent 30-minute payment hold. It supports pickup and, when the Functions runtime variable `NEXA_PHARMACY_DELIVERY_ENABLED=true` is explicitly configured, delivery to a zone common to every cart item; the maximum zone fee is added to the service amount before calculating the transaction fee. The server validates and stores delivery details in NEXA only. `nexaPatientOrders` returns the authenticated patient's laboratory, imaging, pharmacy and nursing order summaries. Diagnostic, pharmacy and nursing Wallet endpoints debit service plus fee atomically and record wallet/fee ledgers. The signed Smart Cut MonCash bridge accepts laboratory, imaging, pharmacy and nursing intents and settles them in NEXA; it sends only `{ paymentRef, amount, currency }` or `{ paymentRef }` to Smart Cut.

Orders pin a 30-minute payment hold. The `nexaExpirePharmacyOrderHolds` scheduler releases expired unpaid pharmacy lot reservations and records stock movements. A paid MonCash callback after expiry is marked for manual review and does not confirm the pharmacy order. The fee policy selects an explicit service override before the general fallback. Until an administrator changes it, the confirmed 3.5% fee applies to all service payments, including Wallet; service-specific overrides are supported. The static admin dashboard manages overrides through `nexaAdminTransactionFeeSettings`; appointment and diagnostic flows use their configured service policies, pharmacy orders use `pharmacy`, and nursing bookings use `nursing_care`. Nursing reservations use a transactionally exclusive provider/week/period hold and can be paid by Wallet or MonCash through the shared signed bridge. A late, conflicting or mismatched MonCash settlement opens an admin reconciliation alert. If the nursing payment and fee amount reconcile but the exclusive period has expired, the order also enters the admin Wallet refund queue; the Wallet credit is limited to the service price, and the transaction fee remains with NEXARIS. The patient can instead request a manual cash refund for that nursing conflict, which moves the alert to the admin settlement queue; NEXA records the cash handoff only after staff confirms the external payment and receipt. After a paid diagnostic order is refused by its provider, `nexaPatientRequestDiagnosticCashRefund` lets its owner request an administrative cash refund; the separate admin review queue records the cash handoff and receipt manually. The pharmacy and nursing checkout tranches are local, untested and undeployed; neither has been applied to Firebase production. App Check Web, Firebase Auth domains, Smart Cut HMAC URLs/secrets and the payment callback still require the usual review/configuration before activation.

## Cross-company MonCash gateway contract

NEXA calls only the Smart Cut functions `nexaMoncashCreatePayment` and `nexaMoncashGetPaymentStatus` in project `smartcutservices-9ce54`, region `us-central1`. Configure the NEXA server URL variables to those exact HTTPS function URLs. Secret values must match across the two Secret Manager projects: NEXA `NEXA_TO_SMARTCUT_SIGNING_SECRET` equals Smart Cut `NEXA_PAYMENT_HMAC_SECRET`; NEXA `SMARTCUT_TO_NEXA_WEBHOOK_SECRET` equals Smart Cut `SMARTCUT_NEXA_WEBHOOK_HMAC_SECRET`. These are two distinct secrets; never use one value for both pairs.

On Smart Cut, set `NEXA_SITE_BASE_URL` to the public NEXA origin and `NEXA_PAYMENT_CALLBACK_URL` to the `nexaMoncashCallback` HTTPS function in project `nexaris-1339d`, region `us-east4`. Smart Cut sends a signed callback containing only the opaque `paymentRef`, `status`, HTG `amount`, `currency`, MonCash `transactionId` and `paidAt`. NEXA compares the reference, amount and currency with its own intent and settles idempotently; the status endpoint is the fallback if callback delivery is delayed. No patient UID, NMC, name, appointment, address, order description or clinical data is sent to Smart Cut. This contract is source configuration guidance only; the URLs, secrets and production functions have not been configured or deployed from this workspace.

For each payment intent, NEXA reuses its unique `paymentRef` across retries; that reference is the idempotency key on both sides. The return URL is intentionally not accepted as a caller-controlled redirect: Smart Cut builds `/paiement/retour/?paymentRef=…` from the allowlisted `NEXA_SITE_BASE_URL` after it verifies the MonCash alert. This fixed NEXA return route supplies the contract's return-URL behavior while preventing arbitrary redirect targets.

`nexaPharmacyProviderOrders` serves the static pharmacy partner portal. It lists only that verified provider's paid, confirmed orders and accepts `accept`, `prepare`, `ready`, `complete`, or `refuse` actions. The endpoint verifies Firebase Auth, App Check, rate limits, the provider profile and order ownership. For an assigned delivery order only, it returns the recipient/contact/address fields required to fulfill delivery; it omits patient UID/NMC and prescription contents. Refusal releases reserved stock and opens the admin refund review; completion consumes reserved lots and confirms pickup or delivery. These provider operations are local, untested and undeployed.

## Pharmacy prescription matching

The pharmacy product schema stores a required administration route alongside dosage/concentration and pharmaceutical form. Prescription availability and order creation require the product route, compare dosage exactly, and reject a route mismatch when the prescription specifies one. Existing published products without a route must be corrected before they can be matched to an ordonnance.

## Static administrator diagnostic review

`nexaAdminDiagnosticResults` serves the separate GitHub Pages admin dashboard. It lists the pending, validated, and patient-visible queues; issues an audited five-minute signed URL only for a CLEAN file under the expected private order/result path; and requires the current admin to open each file before making a review decision. The transaction checks the order, exact exam line and current claim before validation, correction, or marking an exam not performed. A non-performed paid exam creates the existing settlement-review alert; validated performed results can be transferred to the patient with an audit event and minimized notification. Access requires Firebase Auth, App Check, the `NEXA_ADMIN_UIDS` allowlist, CORS and a server rate limit.

The static queue, partner portal and functions are local and not tested or deployed.

## Diagnostic partner contract documents

`nexaAdminDiagnosticPartnerContracts` serves the separate static admin dashboard. It lists laboratory and imaging partners, accepts up to 20 private PDF/JPG/PNG files per partner (10 MiB each), issues short-lived write-once upload policies to a quarantine prefix, checks the declared MIME type, exact size and file signature, then scans fail-closed before moving a CLEAN file to its private contract path. Download links last five minutes and each directory, list and download-link request is audited. `nexaCleanupDiagnosticPartnerContractUploads` runs every ten minutes and removes only objects under the session's exact quarantine/final paths after the cleanup deadline; it does not delete submitted contract records.

This target is HTML/CSS/JavaScript plus Firebase Cloud Functions; the historical Next/Vercel route and cron are not the publication target. Before enabling uploads, configure the private NEXA Storage bucket, exact malware scanner URL/audience and invoker access, Storage CORS for the GitHub Pages admin origin, the runtime signing permissions, App Check and `NEXA_ADMIN_UIDS`. This port is local, untested and undeployed; no partner file or production Firebase data was read or changed.

The separate static administrator dashboard also calls `nexaAdminOverview` for aggregate counts, `nexaAdminAccounts` for a minimal paginated support directory, and `nexaAdminAppointments` for a read-only financial/operational list. `nexaAdminAuditLogs` and `nexaAdminClinicalAuditLogs` expose paginated event projections without free-form notes or clinical content; reading the clinical journal creates an administrative audit event. These endpoints require Auth, App Check outside the emulator, the `NEXA_ADMIN_UIDS` allowlist, CORS and rate limiting. The account directory includes only patient contact/NMC fields or professional public-profile fields; it never returns medical records. This local tranche has not been tested or deployed.

`nexaAdminTransactionFeeSettings` reads and saves the general transaction-fee fallback and per-service overrides in `nexaPaymentSettings/transactionFees`. It validates a 0–100% rate with at most two decimals, assigns the fee to NEXARIS, and writes an audit record. An unset override inherits the general rule. Existing payment records keep their saved total; new appointment, diagnostic, pharmacy and nursing payments read the relevant service policy. The endpoint requires Firebase Auth, App Check, the `NEXA_ADMIN_UIDS` allowlist, CORS and server-side rate limiting. The nursing payment records include the configured transaction fee separately from the total period price.

`nexaAdminProfessionalCommissionSettings` reads and saves nullable, type-specific commission rates in `nexaPaymentSettings/professionalCommissions`. It has no default rates, validates percentages from 0 to 100 with at most two decimals, and writes an audit record. These values are configuration only: no checkout, wallet balance, revenue calculation, or professional payout reads them until NEXA defines the commission base, timing and any reserve. Access requires Firebase Auth, App Check, the `NEXA_ADMIN_UIDS` allowlist, CORS and server-side rate limiting.

## Endpoint

`nexaPatientProfileOnAuthCreate` assigns an NMC number in the Auth creation trigger for registered email, provider-linked and phone-only accounts; anonymous sessions are excluded. `patientProfileInitialize` accepts POST requests with a Firebase Authentication bearer token and a Firebase App Check token, then returns the same idempotently allocated NMC and can save the initial registration fields. The endpoint validates the user, CORS origin, App Check token, and submitted fields.

## Public catalog

publicCatalog accepts GET requests for doctors, laboratories, imaging centers, and pharmacies. It returns only verified, publicly listed profiles; doctor listings also require verified clinical credentials. Responses contain a restricted public profile projection and the approved home-visit tariff and service-area fields only.

`publicProviderAvailability` accepts GET requests for one verified, publicly listed doctor. It returns only future slots with an open or expired hold in the next 90 days, and the public service details needed to show consultation or home-visit availability. Active holds and unpublished profiles are not returned.

`appointmentBooking` accepts authenticated POST requests with App Check. It validates the complete patient profile, doctor eligibility, service fee, home-visit zone, slot length, and current slot state, then creates a 20-minute atomic hold and a NEXA payment intent. Teleconsultations retain a 25-minute video right; home visits retain their service type and contact address only inside NEXA.

`appointmentMoncashCreate` and `appointmentMoncashStatus` require Firebase Auth, App Check, and an intent owned by that patient. They contact only the allowlisted Smart Cut MonCash Cloud Functions using timestamped HMAC signatures. Requests contain exactly `{ paymentRef, amount, currency }` or `{ paymentRef }`, never patient or appointment data. Signed gateway responses are restricted to the payment contract fields; unexpected fields are rejected. The signed callback accepts only the defined settlement fields (`paymentRef`, `status`, `amount`, `currency`, `transactionId`, `paidAt`) and rejects other keys before settlement. It checks the payment reference, amount and currency against the NEXA intent, then settles the appointment idempotently. A fee ledger records the transaction fee for NEXARIS; if payment arrives after the held slot is lost, the system opens a `paymentSettlementAlerts` item for manual review rather than pretending to refund automatically.

`nexaPatientWallet` reads only the authenticated patient's available balance and recent ledger entries. `appointmentWalletPay` atomically debits the total service price plus the transaction fee, confirms the held appointment and records both the Wallet movement and NEXARIS fee. It can only use a fresh appointment payment intent, so an active or completed MonCash attempt cannot be charged a second time. Wallet balances have no cash-out operation; eligible service-price refunds are credited by the admin refund function while the initial transaction fee is retained.

`nexaProviderAvailability` lets a clinically verified doctor list future slots, publish up to 30 new slots at once, and remove only an owned future slot whose status is still `available`. It accepts teleconsultation slots of 30 minutes and home-visit slots of 60 minutes; home visits require an enabled service, configured tariff and at least one service zone. `nexaProviderAppointments` returns the doctor's own appointment summaries, including home-visit address/contact information needed to carry out an assigned mission, allows accepting a paid, confirmed teleconsultation, and lets the doctor complete an active session after both participants connected. The static doctor portal calls `doctorPatientMedicalProfile`, `nexaClinicalRecord` and `nexaClinicalPrescriptions` only on explicit action; clinical notes and prescriptions are restricted to the assigned verified doctor during the paid appointment's active 24-hour clinical window. Notes support versioned drafts, signed finalization and append-only corrections. Prescriptions support drafts, validation/signature, immutable corrected versions, patient notifications and a separate patient list; patient list responses expose only validated prescriptions belonging to the authenticated patient. `nexaPrescriptionAvailability` searches published products with sellable, unexpired stock and published offers from verified partners, ranked by the patient's commune and department; it is read-only and creates no order or reservation. `nexaPrescriptionPdf` streams a generated PDF only to the prescription's patient or its verified doctor during the same active clinical window, and records the download audit. These endpoints use Firebase Auth, App Check, CORS allowlisting, rate limiting and server-side authorization. Prescription validity administration, standalone clinical records and historical records from other encounters remain to migrate into the static portal.

`nexaAgoraToken`, `nexaTeleconsultationPresence`, and `nexaVideoSignal` provide the static teleconsultation path. They require an authenticated patient or the doctor assigned to a paid, accepted teleconsultation, Firebase App Check, and the exact allowed browser origin. Agora tokens are issued for 60 seconds to a stable participant UID and appointment-specific channel; the server limits access to the appointment window and recorded video allowance. `nexaAgoraRtcNotification` accepts only Agora-signed RTC notifications, verifies HMAC-SHA256 or HMAC-SHA1 against the raw request body, deduplicates notices, and uses the participant `clientSeq` to ignore duplicate or out-of-order events. It records RTC communication-mode join/leave events for the appointment channel and participant UID. Only verified join events from both participants set `trustedAgoraRtcStartedAt` and `effectiveConsultationStartedAt`; the client `connected` signal cannot start clinical access or close a no-show refund path. The endpoint acknowledges Agora Console's `test_webhook` health check while the feature flag is false. Set `AGORA_RTC_NOTIFICATION_SECRET` in Firebase Secret Manager, enable RTC events 107/108 in Agora Console, and set `AGORA_RTC_EVENTS_ACTIVE=true` only after the webhook health check succeeds. The default flag is false; video token issuance, call signaling, and automatic provider no-show Wallet credits remain disabled until the server event source is activated. `nexaReconcileTeleconsultationCalls` runs every minute to prune stale presence and classify invitations left unanswered for 90 seconds. After two patient-initiated calls go unanswered by the doctor, it can credit the service price to the NEXA Wallet idempotently; after two doctor-initiated calls go unanswered by the patient, NEXA retains the service price and the doctor receives no payout. The transaction fee is never refunded. A patient cash refund already requested is routed to the separate admin settlement queue rather than receiving a Wallet credit. No credential is stored in the site bundle.

`nexaProfessionalApplication` accepts a physician's authenticated application and returns only that user's application status. It validates and rate-limits submissions, supports resubmission after a rejection, and writes a minimal audit event. `nexaAdminDoctorApplications` is consumed by the separate admin dashboard; its server-side UID allowlist and App Check protect listing and review. Approval requires an explicit credential-verification confirmation and approved consultation fee before the public doctor profile is created. No professional documents are stored by this flow.

These booking/payment functions are local and have not been deployed or run against a payment provider. The first admin refund and reconciliation functions are described below but remain undeployed. App Check web configuration, Firebase Auth domains, both projects' Secret Manager values and Smart Cut function URLs must be configured before activating the public flow. The confirmed 3.5% transaction fee applies to all service payments, including MonCash and Wallet; the payment summary is computed server-side and returned before payment.

## Patient space

`patientAppointments` accepts authenticated GET requests with App Check, verifies that the caller has a complete patient profile, applies a per-user rate limit, and returns only that patient's appointment summary. It does not expose clinical notes. `nexaPatientWallet` returns the caller's Wallet balance and recent financial movements without direct Firestore access. `patientMedicalProfile` reads the patient's initial medical profile through authenticated server requests; writes are denied unless `NEXA_MEDICAL_PROFILE_WRITES_ENABLED=true` is explicitly set after approval of NEXA's health-data privacy notice and consent. The static portal shows any existing profile read-only while writes are disabled. `doctorPatientMedicalProfile` permits a verified doctor to read that profile only for an associated paid appointment within its active clinical access window.

## Separate administration dashboard

`nexaAdminWalletRefunds` also includes paid teleconsultations the doctor never accepted. Those appointments stay `PENDING_REVIEW` without an automatic Wallet credit; an allowlisted administrator can credit only the service price after review. Two unanswered patient calls remain a separate automatic Wallet-refund outcome. Cash requests are handled and recorded manually by administration.

The sibling repository `nexamedcenter-admin` contains a separate static GitHub Pages console. `nexaAdminWalletRefunds` lists eligible payment-conflict appointments and provider-refused orders, then lets an allowlisted administrator idempotently credit only the service price to the patient's NEXA wallet. The original transaction fee remains with NEXARIS; this endpoint does not perform an external refund and rejects a cash-refund request.

`nexaAdminPaymentSettlementAlerts` lists open settlement incidents, records financial-only review notes, and can record a MonCash or cash refund that staff have already completed manually. It never initiates an external transfer. Both functions require Firebase Auth, App Check outside the emulator, allowed CORS origin, rate limiting, and the server-side `NEXA_ADMIN_UIDS` allowlist. They write an audit entry and return only the data needed for the financial queue; they do not expose patient identity or medical profile data.

`nexaAdminNursingServiceSettings` reads/saves NEXA's global nursing periods, zones, total-period tariffs and visit mode (one visit, multiple visits during the period, or modalities agreed after booking), and lets an allowlisted admin review a nurse service profile after credential verification. The selected mode is snapshotted into each new reservation, so a later global setting change does not rewrite an existing booking. Its defaults are AM Monday–Friday 08:00–16:00, PM Monday–Friday 16:00–08:00 the next day, and Week-end Saturday 08:00–Monday 08:00; all days/times remain admin-configurable. Zones start without tariffs, and a profile cannot be approved unless its selected weeks, services, active zones and tariffs are valid. Availability is hidden after the first configured start time of the weekly block in America/Port-au-Prince, and the payment hold is capped at that start. Approval keeps general `publiclyListed` false and sets the separate `nursingDirectoryListed` flag, which enables the public nursing catalog only while the approved profile and its tariffs remain valid. The patient sees the configured visit mode before payment. No professional commission, withdrawal or payout rule is created here.

## Nursing visit scheduling and confirmation

`nexaNursingVisitPlan` lets the assigned verified nurse record an agreed local date/time and the services covered by that visit. The server checks the paid order, the nurse, the purchased service IDs and the booking’s captured mode; `ONE_VISIT` permits one visit entry, while `MULTIPLE_VISITS` and `COORDINATE_AFTER_BOOKING` leave the count and calendar to the nurse/patient agreement. Date checks use `America/Port-au-Prince` and the purchased AM, PM or Week-end interval. No duration, number of visits or professional payout is invented.

`nexaPatientNursingVisits` returns only the authenticated patient’s visit summaries and, while needed, the patient-only code. `nexaPatientNursingVisitFeedback` saves presence, identity match, completed/partial/not-completed status, actual hours, ratings, optional comment and the patient/representative’s explicitly consented electronic-name signature. A fully confirmed service issues an eight-digit code to the patient in the app and, when verified email and Resend are configured, by email. `nexaNursingVisitClose` permits only the assigned verified nurse to enter that code; five invalid attempts lock it for ten minutes, and successful closure deletes the code and its hash. The nurse never receives the patient code through the provider endpoint.

An identity, presence or completion discrepancy enters `nexaNursingAdminVisitReview`. An allowlisted admin reviews the minimized report and chooses code closure or approval of a Wallet credit for the full nursing-period service price; the usual Wallet queue then performs the idempotent credit after confirming no external refund. Transaction fees remain with NEXARIS. Patient-requested cash remains a manual settlement. The report includes an electronic signature and optional comment; approved consent text and a retention/deletion period are still required before deployment. This local tranche was not tested or deployed, and no production Firebase data was read or changed.

These functions and the separate admin UI are local source only. Configure the production UID allowlist and App Check only through the approved secure environment, then deploy only the specific admin functions after review. Do not put these settings or service-account credentials in the browser bundle or repository.

## Project safety

Production execution is guarded to the Firebase project nexaris-1339d. The local Firebase emulator can run with the demo-nexaris project. The repository default remains the emulator project, so any future production deploy must name the project explicitly and deploy only the intended function.

The endpoint uses the Cloud Functions runtime identity for Firebase Admin access. Do not add a service account key to this package. Firestore client rules remain deny-by-default; this function performs its writes with the Admin SDK after server-side validation.

Set NEXA_ALLOWED_ORIGINS as a comma-separated list only when adding a new browser origin, such as a separate admin domain. Current defaults include the public NEXA domain and the Nexaris GitHub Pages origin.

## Home visit mission feedback

`nexaPatientHomeVisitFeedback` stores one patient-signed mission report after the scheduled end and handles an absent-provider refund. A report with a patient-reported identity or service discrepancy enters the NEXA review queue. `nexaAdminHomeVisitMissions` is protected by App Check and the server-side `NEXA_ADMIN_UIDS` allowlist; after case-by-case review it can authorize the provider to close by the patient code or credit only the service price to the patient Wallet. The latter confirms no external refund, validates the original payment and wallet, and writes idempotent refund ledgers and admin audit records; transaction fees remain with NEXARIS. Cash refunds are not part of this action and remain a manual process only when requested by the patient. `nexaHomeVisitMissionClose` verifies the patient-issued eight-digit code for the assigned verified doctor and locks repeated invalid attempts; standard reports must match identity and show a completed or accepted partial service, while a reviewed case may proceed only after the admin authorization is recorded. Firestore and Storage client rules remain deny-by-default; no client-side report access is added. The report contains signature and visit feedback, so retention and consent policy approval are prerequisites to production. The payment settlement functions send the mission code through Resend only when `RESEND_API_KEY` is provisioned as a Functions secret and `NEXA_EMAIL_FROM` is a verified `@nexarishaiti.com` sender. Both MonCash and Wallet use an idempotency key; only a verified Firebase email address receives the code. Before deploying, set the secret with Firebase Secret Manager and place the sender address in `functions/.env.nexaris-1339d`; never put the key in the repository.

## Session text messages

`nexaSessionMessages` is the static-site endpoint for the text and media thread in a paid doctor appointment. GET accepts an `appointmentId` query parameter and returns the 100 latest unexpired messages only to the patient or assigned, currently verified doctor. POST accepts `appointmentId` and a message of up to 4,000 characters; it rechecks the participant, payment, appointment state, interactive end time, and doctor verification in the Firestore transaction before saving. Both methods require Firebase Auth, App Check, an allowed origin, and per-user rate limits. The recipient receives a generic internal notification that does not include message content.

`nexaSessionMediaUpload` creates or cancels a ten-minute, write-once signed Storage policy for a JPEG, PNG, WebP, or supported audio file of at most 15 MiB. Patient photo/voice counts and maximum voice duration come from that appointment's `consultationRights`; the assigned verified doctor can send media without the patient quota. `nexaSessionMediaFinalize` rechecks the session, upload claim, file metadata and limits, sends the file to the private scanner, and only moves a CLEAN file into the appointment's private media path. Voice duration must be returned by the scanner and match the claimed recording within one second. `nexaSessionMediaRead` checks the current participant and exact CLEAN object metadata, audits the access, and returns a five-minute signed read URL. The browser never reads or writes Storage directly and constructs message content with DOM text nodes.

Text and clean media records carry a 30-day expiry timestamp and the read endpoint filters expired entries. `nexaCleanupSessionMessages` runs every 15 minutes and removes up to 400 expired records per pass; it deletes only objects under their exact expected appointment path and keeps the message record if object deletion fails. It also removes expired upload claims only when their quarantine path matches the expected appointment/upload IDs. Before deployment, configure the NEXA private Storage bucket and its browser CORS origins, malware scanner URL/audience and invoker access, signed Storage policy/read permissions, and App Check Web plus production origin. Any missing or non-CLEAN scanner result fails closed. This local tranche has not been tested, built, or deployed; no scanner, Storage object, or production Firebase data was configured or changed here.

La clé métier du bloc est infirmier + lundi de début de semaine + période; une transaction serveur retient ce bloc, puis le confirme au paiement Wallet ou MonCash. Le mode de visite choisi par l’administration est enregistré dans la commande.

## Notifications patient

The static patient portal uses nexaUserNotifications for the latest 60 in-app notifications and individual read status. nexaNotificationPreferences stores opt-in e-mail and push preferences; turning push off also removes that account's server registrations. nexaNotificationPushRegistrations accepts Firebase Installation IDs (FIDs), hashes each ID for its Firestore document key, and enforces account ownership. The nexaUserNotificationDelivery Firestore trigger sends only generic FCM and Resend alerts; message titles, bodies, clinical details, and appointment context stay inside the authenticated NEXA inbox. E-mail delivery requires a verified Firebase Auth address and a verified @nexarishaiti.com sender. The nexaAppointmentReminders Cloud Scheduler runs every five minutes in Port-au-Prince time, creates idempotent 24-hour, 1-hour and 10-minute reminders for confirmed paid doctor appointments, and writes one in-app reminder for the patient and assigned doctor.

Before enabling the external channels, configure RESEND_API_KEY in Firebase Secret Manager. Copy functions/.env.example to functions/.env.nexaris-1339d and set NEXA_EMAIL_FROM as the verified sender plus NEXA_WEB_PUSH_VAPID_KEY as the public Web Push VAPID key. Configure the Firebase Cloud Messaging send permission for the Functions identity. The current notification changes are local and have not been tested, built, or deployed.

## Diagnostic offer administration

`nexaAdminDiagnosticOffers` serves the separate static dashboard's laboratory and imaging offer queue. GET returns only pending and published offers and records the admin list access. POST supports publication, correction requests, rejection, suspension, archiving, and updates to the result-file requirements. Publication rechecks the partner's verified, publicly listed profile and the offer's name and HTG price in the same transaction. Result categories, MIME types, file count, and file size are validated again by the server; order snapshots keep existing purchases on their original requirements. Every decision creates an admin audit entry and a generic partner notification. Requests require Firebase Auth, App Check, the `NEXA_ADMIN_UIDS` allowlist, CORS and rate limiting. The dashboard uses this endpoint without direct Firestore access. Local source only; no test, build, emulator, or deployment was run for this addition.

`nexaAdminDiagnosticPartnerReport` serves a read-only, per-partner activity summary for a verified laboratory or imaging profile. It reports assigned orders and result workflow counts only; it does not calculate commissions, payouts or money due, and does not return patient identities or clinical content. Each read is authenticated, App Check protected, UID allowlisted, rate limited, and added to the administrative audit log. The separate static dashboard calls it from a partner account card.

`nexaAdminDiagnosticCenters` lets an allowlisted NEXA admin correct only the public business profile of an existing laboratory or imaging partner: display name, public phone, address, department, commune, services, and displayed hours. A fixed reason code is required. The function rejects other provider types and does not change verification, listing status, credentials, orders, or financial data. It writes an audit event containing the partner type and changed field names, but not the field values. The separate admin dashboard calls it from the diagnostic partner account card; the browser never accesses Firestore directly. Local source only; no test, build, emulator, or deployment was run for this addition.

`nexaLabSupportTickets` lets only a verified laboratory create and read its non-clinical support tickets. `nexaAdminLabSupport` lets an allowlisted administrator review, answer and change ticket status from the separate static dashboard. Both endpoints require Firebase Auth, App Check, CORS and per-user rate limits; writes are transactional and audit logged, and generic notifications do not include ticket text. The portal warns users not to include patient identifiers or medical information. Imaging accounts cannot open this laboratory-only support flow. These sources are local and have not been tested, built or deployed.


`nexaAdminDiagnosticOrders` sert au dashboard statique séparé une file paginée et en lecture seule des commandes laboratoire/imagerie. Elle renvoie les états opérationnels et financiers, le nom du partenaire, le nombre d’examens et les montants, mais ni identité patient, ni UID/NMC, ni nom ou détail d’examen. Chaque page est protégée par Firebase Auth, App Check, l’allowlist `NEXA_ADMIN_UIDS`, CORS, la limite de débit et un journal d’audit. Cette tranche est locale et non déployée.

## Nursing profile photos

`nexaNursingProfilePhoto` lets an authenticated, App Check-verified nurse upload a profile photo after explicitly consenting to its public display. The server decodes only bounded JPEG/PNG/WebP inputs, re-encodes a small JPEG with Sharp, requires the private malware scanner's CLEAN verdict, and stores it under a private Storage path with no Firebase download token. The separate admin dashboard reviews the photo with the service profile and approves both together before public listing. `nexaNursingPublicCatalog` and the patient's own nursing-visit list verify the nurse, current approval, consent version, object owner and CLEAN metadata before returning five-minute signed image URLs. Configure `NEXA_MALWARE_SCANNER_URL`, `NEXA_MALWARE_SCANNER_AUDIENCE`, scanner invoker permissions and the NEXA bucket before enabling this flow. Local source only; it has not been tested or deployed.

## Doctor profile photos

`nexaDoctorProfilePhoto` applies the same private upload, normalization, malware-scan, consent and temporary-URL controls to verified doctors. The separate admin dashboard approves or rejects each photo. A doctor remains unpublished until approval, and `publicCatalog`, `publicProviderAvailability` and appointment creation require the current approved photo path and consent version. Signed URLs last five minutes; the catalog also verifies the Storage object owner and CLEAN scan metadata before exposing one. Configure the private NEXA bucket, `NEXA_MALWARE_SCANNER_URL`, `NEXA_MALWARE_SCANNER_AUDIENCE`, scanner invoker permissions and App Check before enabling this flow. Local source only; it has not been tested or deployed.

## Pharmacy inventory administration

`nexaAdminPharmacyInventory` serves the separate dashboard with paginated product/lot projections and computed stock alerts for the loaded page: unavailable/low stock, published products without active stock, stored-versus-lot stock mismatches, expired lots, and expiry tiers at 30, 60 and the threshold stored on the product (90 days by default). An allowlisted admin can quarantine an unreserved active lot or restore a non-expired, non-empty quarantined/blocked lot with a required reason. These actions do not change quantities; they append a zero-quantity movement and an admin audit event. `nexaAdminPharmacyStockMovements` exposes a separate paginated movement history. `nexaAdminPharmacyOrders` provides a paginated list and an explicit-detail view of pharmacy order lines and the latest 50 status events. For an order with prescription-required lines, the detail checks the linked prescription’s patient match, validation at order time, any recorded expiry at that time, line references and quantities. It returns only a compliance result and counts: no patient identifiers, contact details, full delivery address, prescribed medication names, notes or prescription content. The read is recorded in `clinicalAuditLogs`; the admin cannot change the prescription or its physician-owned clinical status. Wallet credits use the existing idempotent refund queue, and cash requests go to the manual settlement queue. The order-list query and event-history query use the `nexaOrders(kind, createdAt)` and `nexaOrderEvents(orderId, createdAt)` composite indexes. These endpoints require Firebase Auth, App Check, CORS, rate limits and `NEXA_ADMIN_UIDS`, and the browser accesses neither Firestore nor Storage directly. Inventory alerts are recalculated for each loaded page and are not persisted or acknowledged. Partial refunds/returns, delivery staff, promotions, settings and reports remain to migrate. Local source only; no test, build, emulator, production Firebase access or deployment was performed.
